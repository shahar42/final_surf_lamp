1. System Architecture Overview

1. Data Ingestion

A specialized Python "Worker" polls 3 external APIs (Isramar, OpenMeteo, OpenWeather) every 15 mins to fetch wave/wind data for all active locations.

2. Data Storage

PostgreSQL Database acts as the "Source of Truth". It stores normalized weather data, user preferences, and device configurations.

3. Data Delivery

Lamps (ESP32) wake up every 13 mins, identifying themselves to the Flask API, which queries the DB and returns a 26-byte binary payload.

2. API & Communication Deep Dive

The Core Endpoint: Lamp Data

This is the primary lifeline for all 150+ deployed units.

GET /api/arduino/v3/<arduino_id>/data
Component Details
Trigger Called by ESP32 every 13 minutes (hardcoded sleep cycle).
Security User-Agent: ESP32 header is checked to identify physical devices vs dashboards.
Risk: Spoofable.
Database Action 1. READ: Joins Arduinos table (for ownership) + Users (for settings) + Locations (for cached weather).
2. WRITE: Updates arduinos.last_poll_time = NOW() for monitoring.
Response Content-Type: application/octet-stream
Size: Fixed 26 Bytes (Binary V3 Protocol)

Binary Protocol Structure (V3)

To save bandwidth and processing on the microcontroller, we send raw bytes, not JSON.

Byte Range Name Description
0 - 3 Wave Height Float (Little Endian) - Represents height in meters.
4 - 7 Wave Period Float (Little Endian) - Seconds between waves.
8 Wind Speed Integer (0-255 km/h).
9 - 16 Colors User's custom RGB theme settings (Top/Bottom colors).
25 CRC-8 Checksum to validate data integrity (Lamp discards packet if mismatch).

3. Database & Server Logic

Entity Relationship Flow

The server must "assemble" the lamp's state from three different sources in real-time.

Critical Logic: "Staleness" Handling

The server has intelligent logic to protect the user experience if the background worker fails.

  • Happy Path: Server sees last_updated < 60 mins. Sends fresh data.
  • Stale Path: If last_updated > 60 mins, server sets the stale_flag bit in the binary response.
  • Device Behavior: When the lamp receives the stale_flag, it blinks ORANGE to warn the user the data might be old, instead of showing incorrect "flat" conditions.

4. Visual Status Indicators

The lamp uses a dedicated Status LED (located at the bottom of the center strip) to communicate system health to the user.

Pattern System State Meaning / Action
● Breathing Green Healthy System is online, data is fresh (updated < 30 mins ago).
● Breathing Orange Warning (Stale) Data Staleness: Either the lamp hasn't reached the server for 30+ mins, OR the server has flagged the weather data as "frozen" (unchanged for > 60 mins).
● Breathing Red Data Error The server returned invalid data (e.g., all values are zero). Indicates an upstream provider failure.
● Half Green / Blue Offline The lamp cannot reach the API server. Check WiFi or server status.

5. Critical Technical Findings

⚠️ Security Vulnerability

Device Impersonation: The API trusts any request with User-Agent: ESP32. A malicious user could flood the server with fake device IDs, potentially polluting the last_poll_time metrics or scraping our weather cache.

⚡ "Hang Bomb" Risk

Leftover Debug Code: The background processor contains a while True: sleep loop designed to test the system watchdog. While currently disabled via ENV var, its presence in the production codebase is a risk.
